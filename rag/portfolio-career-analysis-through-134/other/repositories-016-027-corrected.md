### Decision — minimal prose

**Cost:** weak narrative about domain depth, outcomes, responsibility and growth.

# Repository 017 / 134 — `Go-Back-N-Protocol`

## Project identity

**Descriptive name:** **C++ Go-Back-N / Sliding-Window Protocol Study and Console Simulation**

Repository 017 is the first direct corpus evidence of classical data-link/network-protocol study.

The final tree contains four C++ files:

- `GoBackN.h`
- `GoBackN.cpp`
- `Protocol5.h`
- `Protocol5.cpp`

There is no README, build file, automated test suite, socket code, or actual network transport.

The repository contains two related layers:

1. a canonical **Protocol 5 / Go-Back-N sliding-window** implementation structure;
2. a separate console-oriented simulation that asks the user for frames and simulates transmission/errors/retransmission.

The canonical `Protocol5` source closely follows the Go-Back-N listing in Andrew S. Tanenbaum's *Computer Networks*: `MAX_SEQ 7`, `between(...)`, `send_data(...)`, `ack_expected`, `next_frame_to_send`, `frame_expected`, `network_layer_ready`, timeout retransmission and circular sequence numbers. External verification confirms the wording and structure match the published protocol listing. This is therefore strong **study/adaptation** evidence, not original algorithm invention.

More importantly, the transport abstraction functions in the repo are stubs, so the canonical protocol is not a complete runnable networking stack.

## 6. Correctness issues

A particularly serious issue appears in the `send_data` logic of the console implementation: a `packet` value is assigned into the frame's numeric acknowledgment field.

That is type-incompatible under the shown structures and can make the file fail to compile or require unintended conversion.

This strongly limits runnable-code confidence.

Other maturity weaknesses include:

- duplicated protocol concepts across two implementations;
- empty transport hooks;
- no error checking around user input;

## 5. Major correctness defects

The implementation contains several important bugs.

### Engine-off quit mismatch

The menu describes one input for quitting, but code checks for a different character (`'c'`).

As a result, the displayed quit option does not correctly terminate the application.

### AC control `if / if / else` defect

For low temperature:

1. first `if` turns AC on;
2. second independent `if` evaluates false;
3. its paired `else` immediately turns AC back off.

Thus the low-temperature branch is effectively overwritten.

### Engine-temperature controller has the same defect

A low-temperature activation can similarly be overwritten by the second `if`/`else`.

### Temperature input is read as a character

`%c` is used where numerical temperature semantics are expected.

That means input represents an ASCII character code, not a numeric temperature value.

### `char` is used for temperature values

Values up to ~150 are compared/stored.

On implementations where `char` is signed, this can overflow and invalidate comparisons.

### Unnecessary pointer/input behavior

Some function arguments are immediately replaced by struct state, making the passed value meaningless.

### No validation

Invalid menu/sensor inputs are not robustly handled.

## 26. Engineering decisions and tradeoffs

### Decision — custom loop instead of a game engine

**Benefit:** exposes timing, rendering and input mechanics directly; strong learning value.

**Cost:** the developer must personally handle lifecycle, synchronization, physics, assets and architecture that an engine would otherwise provide.

### Decision — separate update target and frame target

Targeting 200 UPS and 120 FPS shows awareness that simulation updates and rendering need not be identical.

**Benefit:** conceptual separation of simulation and presentation.

**Cost:** the busy loop can consume CPU aggressively, and no catch-up cap prevents spiral-like behavior under load.

### Decision — boolean input/state flags

**Benefit:** simple and readable for a small prototype.

**Cost:** state combinations can become inconsistent as features expand. An explicit state machine or input-command abstraction would scale better.

### Decision — inheritance (`Protagonist extends Character`)

**Benefit:** establishes shared character abstraction.

**Cost:** with only one concrete actor and little generalized behavior, inheritance may be premature; composition would become more flexible for a larger game.

## 2. Design behavior

The DUT `MMC_Game` implements a 3-bit circular counter controlled by two-bit modes:

- up by 1;
- up by 2;
- down by 1;

This gives a compact stateful design with:

- wraparound;

## 11. Sequential timing / score latency

Winner/loser flags are assigned in one clocked block, while score counters consume those flags in another clocked block.

This creates implicit multi-cycle latency.

It may be acceptable if intentionally modeled, but it is not documented and complicates test timing.

## 29. Engineering decisions and tradeoffs

**Benefit:** readable conceptual decomposition.

**Benefit:** easy to write.

**Benefit:** moves from waveform inspection to explicit pass/fail aggregation.

## 31. Mistakes / anti-patterns / likely lessons — expanded

### Multiple procedural ownership

Signals driven from multiple `always` blocks create ambiguity and synthesis risk. The likely lesson is to define **one sequential owner per state register** and derive combinational next-state separately where appropriate.

### Nonblocking-assignment latency

A downstream clocked block sees the previous cycle's value. Score/game-over logic therefore contains hidden pipeline-like latency. This is not necessarily wrong, but undocumented latency is a verification hazard.

### Fixed-delay tests

Testing by “wait N time units then inspect” becomes brittle. Clock-event synchronization and reusable tasks make intent clearer.

### Incomplete test-results array

A self-checking report is only as trustworthy as its bookkeeping. Uninitialized/unassigned slots can produce false failures or ambiguous output.

### Missing dependency

A repository that references `clock.sv` but does not contain it cannot reproduce cleanly from checkout.

## 21. Engineering decisions and tradeoffs

### Decision — DOM elements instead of Canvas/WebGL

**Benefit:** easy styling/debugging and no drawing API setup.

**Cost:** 150 independently positioned elements plus frequent layout reads/writes are expensive compared with a canvas-based renderer.

### Decision — `setInterval(...,16)`

**Benefit:** simple approximation to 60 updates/s.

**Cost:** not synchronized to browser rendering; interval drift and background-tab throttling can distort motion.

### Decision — all-pairs collision checks

**Benefit:** simple and correct in concept for small N.

**Cost:** O(n²) work. At 150 balls the implementation already performs tens of thousands of directed comparisons per update.

### Decision — direct GitHub Pages workflow

**Benefit:** static deployment is proportionate to a no-build single-page project.

**Cost:** workflow execution was never observed, so configuration confidence exceeds operational confidence.

## 37. Engineering decisions and tradeoffs — expanded

### Voxel downsampling

**Benefit:** reduces point count and processing cost.

**Tradeoff:** coarse voxel resolution can erase small objects/detail.

The presence of a configurable resolution demonstrates awareness that perception quality and computational load trade against each other.

### ROI cropping

**Benefit:** removes irrelevant space and reduces computation/noise.

**Tradeoff:** an overly narrow ROI can discard relevant obstacles.

### Ego-roof removal

**Benefit:** prevents the vehicle's own geometry from being clustered as an obstacle.

**Tradeoff:** hardcoded crop bounds assume a specific sensor/vehicle geometry.

### RANSAC distance threshold / iteration count

**Benefit:** controls plane-fit robustness and runtime.

**Tradeoff:** threshold choice affects road-vs-obstacle classification.

### Cluster tolerance and min/max sizes

**Benefit:** tunes object grouping and rejects tiny/huge components.

**Tradeoff:** wrong parameters can merge adjacent objects or fragment one object.

### Use PCL rather than from-scratch algorithms

This is an appropriate engineering decision for application integration: trusted library primitives let the learner focus on pipeline behavior.

The tradeoff is that algorithmic implementation depth should not be overstated.

## 38. Mistakes / anti-patterns / likely lessons — expanded

### Visualization-loop brace defect

Placing `viewer->spinOnce()` outside the main loop can undermine PCL viewer responsiveness and reveals the importance of control-flow review even in visually testable systems.

### Raw ownership

Using `new` without visible cleanup is acceptable in a short-lived exercise but poor modern C++ ownership discipline.

Likely lesson:
- prefer RAII / smart pointers when ownership is local and clear.

### Fragile/legacy CMake

Global include/link flags and suspicious flag syntax make the build less robust than modern target-based CMake.

### No regression harness

Parameter changes are evaluated mainly visually. That makes it hard to know whether a tuning change improves one frame while degrading others.

### Course-starter leakage

Retaining externally authored docs/comments without explicit learner-vs-starter boundaries can cause provenance confusion later.
